# Security items from the duplication audit: break it (2026-10-31)

**Process:** quality mandate step 4. The audit (`docs/engineering/duplication-audit/`) compared copies of the same code and flagged places where one copy checks more than another. These points were listed and checked against the code, the migrations and the server rules **before** any fix. Each fix then gets its own failing test first (step 5).

| # | Attack or failure | Checked against the server | Status |
|---|---|---|---|
| AS-01 | **Guessing a verification code with many requests at once.** `verify-contact-otp` reads the wrong-guess count, compares, then writes count + 1. Requests sent at the same moment all read the same count, so the 5-guess cap doesn't hold. A 6-digit code is valid for 10 minutes and there is no limit on verify calls. Winning marks an email, phone or guardian phone as verified that the attacker doesn't own. | Real. Nothing on the server counts guesses atomically. | **Fixed:** each guess first claims one attempt atomically (`UPDATE … WHERE attempts = n`), so a guess that loses the race is never compared (`_shared/otpCheck.ts`). Plus a cap of 30 verify calls an hour per contact, failing closed. Tests: `otp-attempts`, simulation (500 attackers × 2,000 guesses: never more than 5 compared). |
| AS-02 | **Reopening or re-resolving a closed dispute.** Live `escalateDispute` sets `open` from any status; live `resolveDispute` doesn't check the status is `open`. The demo copies check both. The server trigger `guard_dispute` lets a match manager make any status change. | Real, narrow: only the match's own managers (who can already edit the match) can do it. A dismissed dispute with both captains' earlier confirmation could still move stats. | **Fixed:** only the four moves the screen offers (reported → open/dismissed, open → resolved/dismissed), in the app (`core/disputeFlow.ts`, demo and live) and on the server (migration `20261031150000_dispute_status_flow.sql`). Tests: `dispute-status-flow`, simulation (500 disputes, 1,500 bad moves refused). |
| AS-03 | **A guest sees a restricted player's per-sport profile.** SportProfileScreen gates guests on age only; PlayerProfileScreen also checks `restricted`. | **Not a leak.** For a logged-out viewer the view marks a player restricted exactly when they are not a proven adult (`full = adult`), and then also hides their `age`, so the age-only gate already blocks them. | Holds, no change |
| AS-04 | **Phone sign-up: a US child under 13, or an under-18 with only a guardian phone.** The phone card lacks the US under-13 message and accepts a guardian phone instead of an email. | **Not a security hole.** The profile trigger (`privacy_on_new_profile`) rejects US under-13 accounts on every path, and every under-18 account starts `pending` (limited) until a parent approves. But the phone path shows a vague "couldn't create your account" error, and with no guardian email the parent's approval link can't be sent, so the child is stuck. | **Fixed:** the phone card and `phone-login` now ask what email sign-up asks: the plain US under-13 message, and a guardian email for every under-18 (`_shared/minorSignup.ts`). Tests: `phone-signup-minors`, simulation (1,000 random sign-ups). |
| AS-05 | **Faking the caller's IP to get around phone-login's per-IP limit** (`x-forwarded-for`'s first entry). | **Not confirmed.** Supabase's docs don't say whether the platform overwrites or appends this header. Low impact: phone login also needs a real SMS code checked by Google, and there is a per-number limit (10 an hour). | Open, needs a platform check |
| AS-06 | Invites and org-verification emails sent to any typed address, with limits that fail open. | Reported by slice 04, not re-checked here. | Next round |
