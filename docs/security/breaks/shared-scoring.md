# Shared scoring: break it (2026-11-03)

**Feature (founder approved):** two or more listed scorers record the same match at the same time from their own phones (a pool game: while one plays, the other records, and vice versa). Today exactly one phone may write (the scoring lock, migration `20261019120300_scoring_lock.sql`).

**Design:** a per-match switch `matches.shared_scoring` (off by default). In shared mode the single-holder lock is not used among the people who may score; instead every tap carries its **base** (the key of the newest event the phone had applied: its client id, else `id:<row id>`; `''` for an empty log), and the server refuses a tap whose base is not the match's newest event (optimistic concurrency). Undo is base-checked the same way. Migration: `supabase/migrations/20261103120000_shared_scoring.sql` (file only; the founder runs it).

**Process:** quality mandate step 4. Points S1–S20 were listed after reading the code and **before** any fix (all Open); each fix then got a failing test first (step 5). S21 was found by the simulation.

| # | Failure | Status |
|---|---|---|
| S1 | **Double count.** Two phones both record the same pot within a second; with the lock off both inserts would land. | **Fixed:** every tap carries its base (`baseOf`); in shared mode `append_match_event` refuses a tap whose base isn't the newest event (`stale_tap:<player id>`) and inserts nothing. db test S1/S2; sim (no step ever twice). |
| S2 | **A tap applied to a moment that has moved on.** A taps on a board where it is player 1's turn; B's tap already passed the turn. | **Fixed:** same base check — a tap only lands on the exact board it was made on. The sim proves the server log is a chain (each step based on the one before). |
| S3 | **Undo removes the other person's step.** A presses Undo meaning their own pot, but B's newer step is now the newest row. | **Fixed:** `pop_match_event(p_match, p_device, p_base)` is base-checked in shared mode: it removes only the step the phone saw as newest, else `stale_tap` and nothing is removed; the phone refreshes and says who. The Undo bar names who recorded the step ("Undo: pot · recorded by Ashok"); undoing another person's step asks first. **Deviation:** Undo stays a server-side removal of the newest row (not an inserted UNDO row), so every replay and viewer keeps working; it is serialised by the same base check. |
| S4 | **ABA after undo.** B undoes seq 11 and records a new step at seq 11; a seq-only check would pass A's tap. | **Fixed:** the base is the event's key (client id, else its never-reused bigint row id), not its seq. db test S3/S4. |
| S5 | **A stranger writes in shared mode.** | **Holds:** `can_manage_match` is checked first in both functions (listed scorers, hosts, tournament organisers); others get `not_active_scorer`. db test S5. |
| S6 | **Old app versions** send no base. | **Fixed:** an old app's call (resolved to the new signature, `p_base` null) is refused in shared mode with `update_app_shared_scoring`; its outbox puts the taps in the review list ("Update SportnNote…"). Old apps keep working in one-at-a-time. db test S6. |
| S7 | **Direct table writes bypass the check.** | **Fixed:** `guard_match_event_write` refuses direct client inserts / deletes on a shared match while it is played (a whole-match delete cascading one trigger level down is still allowed). db test S7. |
| S8 | **Who may switch it.** A tournament match's listed scorer turns it on; anyone flips the column directly. | **Fixed:** `set_shared_scoring` RPC — friendlies: `can_manage_match`; tournament matches: the match's hosts or `can_manage_tournament` only. A trigger refuses direct client updates of the column and forces it off on client inserts. Client mirror `canSwitchShared`. db test S8. |
| S9 | **Offline queue silently merged.** | **Fixed:** queued taps carry their base; a tap made offline (or whose send failed) is marked `waited`, and a stale refusal of such a queue goes to the existing review list (rejectedCount / Discard), never merged. The sim found that the first version (age only) dropped a tap made offline and synced within 15 s; fixed with `waited`. |
| S10 | **Refusal loops / no explanation.** | **Fixed:** `outboxOnError` — stale live taps (all fresh, none waited) are dropped at once, their stats reversed, the board refreshed, and "Ashok just recorded a step — your tap wasn’t added" shown (clears after 6 s). Never retried. |
| S11 | **Chained queued taps.** Tap 1 is refused; tap 2 (based on tap 1) lands on some other row. | **Fixed:** a stale head drops / reviews the whole queue (each queued tap is based on the one before). sim. |
| S12 | **Retry after success refused.** | **Holds:** the idempotent client-id check runs before the base check; a retried tap that already landed returns its seq. db test S12. |
| S13 | **Lock left behind / re-taken.** | **Fixed:** switching on clears the lock holder; `claim_scoring` in shared mode returns ok without taking the lock; `getScoringLock` reports `shared` and the client's `lockStatus` is `shared` (everyone allowed may write). db test S13. |
| S14 | **Hand over in shared mode.** | **Fixed:** `handover_scoring` refuses (`shared_scoring_on`); the Match scorers card shows no Hand over and lists every scorer as "Can score now" (CAN SCORE). |
| S15 | **Spoofed "recorded by".** | **Fixed:** `recorded_by` (a player id) is set only by `append_match_event` (`my_scoring_player`); the guard trigger blanks it on any direct client insert. db test S15. |
| S16 | **Children's data.** | **Holds:** events stay IDs-only — `recorded_by` and the stale message carry a player id; the phone names them through the names it may already see (scorer list / mask). No names are added to rows or errors. |
| S17 | **One-at-a-time changed.** | **Holds:** with `shared_scoring` false (every existing match) the functions run 0039's exact branches and ignore the base; the old signatures are replaced by ones with a defaulted `p_base`, so old apps' named calls resolve unchanged. The client falls back to the old call on a database without the migration. db test S17 + every existing lock test. |
| S18 | **Abuse: flooding to make the other phone stale.** | **Accepted:** only a trusted scorer of that match can do it (they could equally record wrong steps); the refused phone is always told who. No rate limit existed on this function before; none added. |
| S19 | **Reset / finish while the other phone taps.** | **Accepted:** `reset_match` and finishing are unchanged, confirmed actions; the other phone's realtime DELETE / status change rebuilds its board, and its in-flight tap is then stale, or after finish a post-match write under today's rules. |
| S20 | **Info doesn't say how the match is scored.** | **Fixed:** Info › Rules & stats captured starts with "Scoring: Shared — several phones at once / One phone at a time" (`scoringRule`). |
| S21 | **A late retry brings back an undone step** (found by the simulation). A's reply is lost, B undoes A's step, A's outbox retries the same client id on its old base, which is the newest again. | **Fixed:** shared-mode Undo records the client id in `match_event_undone` (RLS on, no policies); a later append of it is `stale_tap`. Mirrored in `serverDecision({ undone })`; db test S21; sim invariant "an undone step never comes back". |
