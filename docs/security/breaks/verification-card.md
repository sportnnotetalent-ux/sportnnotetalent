# Age & guardian verification card: break it (2026-11-03)

**Source:** founder request. The profile's "Age & guardian verification" card showed everything inline (long explanation, Re-submit, red support note, the full history). It becomes a compact card (title, status chip, one line for what to do next, "Details ›", and the primary action only when one is needed); the full content moves to its own screen (`VerificationDetails`).

**Process:** quality mandate step 4. Listed after reading the code and **before** any change. Each fix then got its own failing test first (step 5).

| # | Failure | Status |
|---|---|---|
| P1 | **Privacy: the details screen is a new door.** A route takes a `playerId`, so anyone could open `VerificationDetails` for any player (deep link, a crafted navigate) and read the status, support note and history. | **Fixed:** the screen resolves the viewer's own player (`getMyPlayerId`) and shows the record only when `canSeeVerification` (own player, or support); anyone else gets "Only the player can see this". Test P1; sim (600). |
| P2 | **Privacy: the card's gate must not widen.** Today only the owner (`onEditProfile`) or support (`player.verification && isSupport`) sees the card. The compact card must keep exactly that gate. | **Fixed:** the gate in ProfileView is unchanged. Test P2 + the existing privacy test. |
| P3 | **Privacy: documents are never shown to others.** Only a support reviewer may open the document (signed URL); the owner and everyone else never get a "View document" button, and the history never shows the raw file name (`docKindLabel`). | **Fixed:** "View document" sits only in the reviewer block of the details screen; the history goes through `historyRows` (the file's kind, never its name). Test P3/H1; sim. |
| S1 | **Every status gives one clean line.** Not started, pending, rejected, approved, and the fast lanes (school / parent confirmed) each need a short next step; an unknown or missing status must not print `undefined` or an empty line. | **Fixed:** `verificationSummary` (core/verificationReview.ts): chip Verified / Pending / Rejected / Not started + one sentence; unknown → Not started. Test S1; the sim checks one sentence, ≤ 90 chars, no `undefined`. |
| S2 | **The rejected line says what to do**, not just "Rejected": "Upload a clearer photo of a birth certificate, school ID or passport." | **Fixed:** exactly that line. Test S2. |
| S3 | **The pending line reassures**: "We're checking your document …" — and no upload button is pushed on the card while a review is running. | **Fixed:** "We’re checking your document, usually within a few hours." and no action on the card (Re-submit stays on Details). Test S3. |
| S4 | **A reviewer viewing someone else's profile** reads a reviewer line (not "upload …", which is the owner's job). | **Fixed:** reviewer lines ("Waiting for a review, open Details …"), never an action. Test S4; sim. |
| A1 | **No lost actions.** Upload (first time), Re-submit (pending or rejected), View document, Approve, Reject with a reason: every one must still be reachable (card or details screen). | **Fixed:** upload / re-submit is one shared hook (`useVerificationUpload`) used by the card and Details; Re-submit while pending, View document, Approve, Reject + reason are on Details. Test A1. |
| A2 | **The card's primary action** shows only when the owner must act (not started → Upload, rejected → Re-submit); never on approved / confirmed / pending, never for a reviewer. | **Fixed:** `summary.action` only for the owner on Not started ("📎 Upload proof") or Rejected ("📎 Re-submit proof"). Test A2; the sim checks every combination. |
| A3 | **Stale card after acting on the details screen.** After an upload or a decision on the details screen, back on the profile the chip must show the new status (the profile reloads on focus). | **Fixed (by design):** `usePlayerProfile` reloads on focus, so the card re-reads the status on return. |
| G1 | **Guardian view.** The card is the same component wherever it appears; a parent who manages the child's own login sees the same compact card. (The linked-guardian screen `ManageChild` never showed this card; unchanged.) | **Fixed:** one `VerificationCard` component, used wherever the card appears. |
| H1 | **History only on the details screen**, complete (submitted / approved / rejected), with dates (day month year) and the rejection reasons; a bad timestamp shows "—", never "Invalid Date". | **Fixed:** the profile has no history / support note / long text; Details lists every entry with "5 Mar 2026" dates and "Reason: …"; a bad time shows "—". Test H1; sim. |
| K1 | **Keyboard:** the reviewer's reason field lives on the details screen, which must scroll above the keyboard (KeyboardAwareScrollView). | **Fixed:** Details uses `KeyboardAwareScrollView` (`keyboardShouldPersistTaps="handled"`). Test K1. |
| X1 | **Accessibility:** the "Details ›" link has a role and a label; the chip and buttons keep readable labels; emoji-leading text goes through IconText. | **Fixed:** "Details ›" is `accessibilityRole="link"`, label "Verification details" + hint; each history row has one spoken label; emoji-leading lines use `IconText`. a11y-labels and leading-emoji tests pass. |
